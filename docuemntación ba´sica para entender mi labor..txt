Un README es el archivo de presentación de un repositorio: GitHub lo renderiza automáticamente en la página principal del proyecto, justo debajo de la lista de archivos. No es código, es documentación de entrada, y su función práctica es que quien llega sepa en 30 segundos qué está mirando.

Para qué se usa de verdad:

Explicar qué hace el proyecto y por qué existe. El problema que resuelve, para quién es y en qué se diferencia de las alternativas.
Decir cómo instalarlo y ejecutarlo. Dependencias, versión del lenguaje, comandos, variables de entorno. Sin esto, nadie prueba tu código.
Mostrar un ejemplo de uso mínimo. Un fragmento corto que funcione vale más que párrafos de teoría.
Documentar cómo contribuir. Cómo reportar bugs, abrir un pull request, estilo de código, guía de commits.
Declarar la licencia. Sin licencia explícita, legalmente nadie puede reutilizar tu código con seguridad.
Créditos, capturas, badges de estado de CI, enlaces a la demo o a la documentación completa.
Atraer colaboradores y usuarios. En proyectos open source es el principal factor de adopción: un repo sin README parece abandonado aunque esté activo.
Cómo funciona técnicamente: si el archivo se llama README.md, GitHub lo detecta y lo muestra como portada del repo; además aparece en los resultados de búsqueda y en el perfil. El .md permite Markdown: títulos, tablas, bloques de código con resaltado, imágenes y enlaces. También puede haber README dentro de subcarpetas para documentar módulos concretos.

Cuándo no hace falta: repos de pruebas, apuntes personales, o cuando la documentación vive en otro sitio y el README solo enlaza a ella. Aun así, un par de líneas explicando qué es el repo ahorra confusión.

Si quieres, te redacto un README completo con estructura, secciones y textos listos para rellenar con los datos de tu proyecto.

Depende de qué estés licenciando, porque "página web" puede ser tres cosas muy distintas y cada una pide lo contrario. Te lo separo:

1. Un sitio o SaaS que es tuyo y quieres monetizar
La licencia casi no importa mientras no publiques el código: si no lo distribuyes, el código es tuyo por defecto. Cuando lo subas a un repo público, la opción con más retorno es AGPL-3.0: obliga a quien use tu código como servicio a liberar sus modificaciones, así un competidor no puede levantar tu mismo producto, cerrarlo y venderlo. Si el proyecto es sobre todo frontend estático sin valor en el backend, AGPL no protege nada y MIT es suficiente.

2. Una librería, componente o plantilla que quieres que se use mucho
Aquí el objetivo es adopción, y la adopción se compra con permisividad: MIT (o Apache-2.0 si te preocupan las patentes). Cualquier licencia copyleft fuerte espanta a las empresas, porque su departamento legal no quiere arrastrar obligaciones. Contrapartida real: con MIT un competidor puede tomar tu plantilla, cerrarla y venderla sin devolverte nada. Si eso te molesta, BUSL o Elastic License 2.0 te permiten mantenerla abierta y vetar la explotación comercial por terceros.

3. Trabajo para un cliente
No uses licencia open source. Redacta contrato con cesión de derechos patrimoniales al cliente tras el pago, y resérvate expresamente el código de base, frameworks propios y componentes reutilizables. Si entregas con MIT, el cliente puede revender tu trabajo a un tercero y tú pierdes la exclusividad.

Resumen por objetivo

Objetivo	Licencia
Máxima difusión de una librería	MIT
Difusión + protección de patentes	Apache-2.0
Producto monetizable, evitar clones	AGPL-3.0
Open source pero sin competencia SaaS	BUSL / Elastic 2.0
Entrega a cliente	Propietaria + cesión contractual
Recursos que sí conviene licenciar aparte: tipografías con SIL OFL, imágenes con CC0 o de bancos con licencia comercial explícita, y librerías JS con su licencia original intacta. Un package.json sin license deja el proyecto en "todos los derechos reservados" por defecto, y eso rompe la cadena de dependencias para quien lo integre.

Mi recomendación concreta: si el sitio es tu negocio, código privado y AGPL solo si publicas; si es una plantilla para vender, MIT para la parte gratuita y una licencia comercial de pago para la versión extendida. Ese doble carril es el que de verdad da frutos sin regalar el activo.

¿Es un proyecto propio, una plantilla para vender o trabajo para un cliente? Con eso te digo el texto exacto del archivo LICENSE y qué cláusulas añadir.
